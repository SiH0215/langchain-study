# 기초 프로젝트를 점검하는 방법

## 1. Tool과 Agent

Tool은 입력·출력이 정해진 함수. 타입 힌트는 입력 스키마를 만들고 docstring은 언제 쓰는 도구인지 설명.
함수 이름만큼 설명도 중요. `multiply(a: int, b: int)`처럼 범위가 작은 함수로 시작.

```text
질문 → 모델이 도구 이름·인자를 요청 → 실행기가 함수 실행
     → ToolMessage로 결과 전달 → 모델이 최종 답변
```

모델이 `tool_calls`를 출력하는 것과 Python 함수가 실행되는 것은 다름.
`model.bind_tools(...)`는 도구 정보를 모델에 전달. 직접 호출만 하면 실행 루프는 개발자가 직접 처리.
`create_agent`는 이 반복 실행 구성. 예제는 결과 메시지와 도구 요청을 출력해 실제 동작 관찰.
곱셈의 예상 정답은 391이며 실제 모델 답변은 실행 후 확인.

`InMemorySaver`와 같은 `thread_id`를 사용하면 후속 호출까지 상태 유지.
다른 대화는 다른 ID를 쓰고, 프로세스가 끝나면 메모리 저장 상태는 소멸.
예제의 `recursion_limit=10`은 그래프 실행 단계 제한. 정확히 10회 모델 호출이나 비용 상한을 의미하지 않음.
도구 실행 오류·잘못된 인자·불필요한 반복이 생기면 실행 기록을 보고 수정.

에이전트가 꼭 필요한지 우선 판단. 번역 한 번, 정해진 검색 한 번이면 체인이나 고정 흐름이 더 단순함.
LangGraph의 노드·분기·상태 설계, 사람 승인, Agentic RAG는 다음 단계.

## 2. 단계별 오류 점검

| 현상 | 먼저 확인할 것 | 대응 |
| --- | --- | --- |
| ModuleNotFoundError | 설치한 Python과 실행 Python 일치 여부 | `python -c "import sys; print(sys.executable)"` |
| ImportError | 블로그 코드와 설치 버전 차이 | 공식 문서·검증 버전 확인 |
| 키 없음 / 401·403 | .env 위치, 키 권한, 사용 API | 키 자체를 로그에 출력하지 않고 설정 확인 |
| 모델 없음 / 404 | 모델 ID와 계정·지역 지원 | .env의 모델 ID 수정 |
| 429 | 요청 수·토큰·계정 쿼터 | 병렬 수 축소, 재시도 간격, 쿼터 확인 |
| timeout / 5xx | 네트워크·공급자 상태·응답 길이 | 제한된 횟수만 재시도 |
| 프롬프트 키 오류 | 입력 dict와 템플릿 변수 | 모델 호출 전 prompt.invoke 확인 |
| JSON 검증 오류 | 스키마와 실제 응답 | 요구 필드·지원 방식 확인 |
| RAG 오답 | 정답 문서가 검색됐는지 | 검색과 생성을 분리해 점검 |
| 후속 질문 오답 | 재작성 질문과 전달된 history | 주어가 유지되는지 확인 |

키 누락·잘못된 모델 ID를 무한 재시도해도 해결되지 않음.
예제 모델은 timeout 60초와 제한된 재시도를 설정하지만 전체 작업 시간·비용의 엄격한 상한은 아님.
학습 중에는 경고를 일괄 숨기지 않음. 예제는 기존 기록의 경고 숨김 처리를 가져오지 않았음.

## 3. 비용·시간·컨텍스트

문서 임베딩, 질문 임베딩, 질문 재작성, 최종 응답을 별도 호출로 집계.
`--search-only`도 임베딩 호출이 있음. history-aware는 후속 질문마다 재작성 호출이 추가.
batch·재시도·에이전트 반복도 호출 수를 늘릴 수 있음.

모델의 `usage_metadata`로 제공되는 입력·출력 토큰 정보를 확인하고 `time.perf_counter()`로 경과 시간 측정 가능.
모델별 요금이 다르므로 토큰 수만으로 금액을 단정하지 않음.
문자 길이·메시지 수·토큰 수를 혼동하지 않음. 검색 문서와 전체 대화도 입력 토큰 사용.
스트리밍은 첫 화면 표시를 앞당기지만 전체 응답 시간이 항상 짧아지는 것은 아님.

## 4. 답변 품질을 작은 질문 세트로 확인

정답이 있는 질문, 없는 질문, 후속 질문, 비슷한 표현을 함께 준비.
정답 문서가 top-k에 포함됐는지와 답변이 근거를 따르는지를 따로 기록.
예를 들어 문서 포함률이 좋아도 모델이 숫자를 바꿔 말하면 생성 단계 문제.
질문 3개를 통과한 것을 전체 정확도 100%라고 쓰지 않음.

| 관찰 항목 | 직접 기록할 증거 |
| --- | --- |
| 검색 | 질문, 재작성 질문, 검색 문서·점수 |
| 생성 | 응답, 인용한 원문, 문서 밖 정보 여부 |
| 기억 | 이전 발언을 유지하는지, 초기화 후 잊는지 |
| Agent | tool_calls, ToolMessage, 최종 결과 |
| 성능 | 호출 수, 토큰, 경과 시간, 오류 |

LangSmith는 체인·도구 호출 흐름을 추적하고 비교할 때 쓰는 선택 도구.
이 저장소는 자동 활성화하지 않음. 사용하려면 [공식 추적 안내](https://docs.langchain.com/langsmith/observability-quickstart)에 따라 워크스페이스·키·대상 설정.
추적에는 프롬프트·문서·응답이 담길 수 있으므로 어떤 데이터가 전송되는지 확인.

## 5. 공개 저장소와 재현

실제 키는 `.env`, 공유할 설정 이름은 `.env.example`에 보관.
`.gitignore`는 아직 추적하지 않는 파일 제외. 이미 커밋한 비밀을 이력에서 지우는 기능은 아님.
요구 범위는 requirements.txt, 이번 검증 버전은 requirements-lock.txt에 기록.
실행 루트, 모델 ID, 패키지 버전, 입력 문서를 함께 기록해야 다른 사람이 결과를 해석 가능.

## 6. 기초 이후 확장

| 다음 단계 | 현재 예제에서 바꿀 부분 | 완료 조건 |
| --- | --- | --- |
| 여러 문서 | Document에 source를 각각 부여 | 서로 다른 문서 출처 확인 |
| PDF RAG | 로더와 페이지 metadata | 표·스캔 문서의 한계 기록 |
| 영속 벡터 저장소 | 인덱싱과 질의 분리 | 재실행 시 인덱스 재사용 |
| 검색 개선 | MMR·필터·하이브리드·리랭킹 | 같은 질문 세트로 개선 비교 |
| 토큰 기반 대화 제한 | 단순 문답 자르기 교체 | 오래된 대화와 긴 입력 처리 |
| Agentic RAG | 검색을 Tool로 노출 | 재검색·종료 조건과 근거 관찰 |
| LangGraph | 상태와 분기 명시 | 분기·재시도·복구 실험 |
| 서비스화 | CLI를 API·UI로 확장 | 사용자 분리·동시성·운영 로그 |

위 항목은 앞으로 할 실습이며 이번 구현 완료 목록이 아님.
